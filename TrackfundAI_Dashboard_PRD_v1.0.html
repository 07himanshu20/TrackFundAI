TrackfundAI Dashboard

Product Requirements Document · Version 1.0 · 29 August 2026 · Confidential

1. Introduction & Product Overview

1.1 Purpose of this document

This document describes what the TrackfundAI Dashboard does and why it is designed the way it is. It is written for a business partner and is meant to be read end to end by both technical and non-technical stakeholders. It explains the product at a conceptual level: the behaviour a user can rely on, the guarantees the system makes, and the reasoning behind the design. It deliberately does not describe how the system is built at the level of code, components, or third-party technology.

1.2 What the product is, in one paragraph

A fund manager receives financial data from many sources — portfolio schedules, capital accounts, valuation statements, distribution notices — as a large number of separate Excel files, each in its own layout. The TrackfundAI Dashboard turns that scattered, inconsistent pile of files into a single, governed picture of the fund. It does this in two connected stages that together form one product. First, a pre-ingestion layer reads every file, locates the figures that matter, verifies them, and consolidates them into one authoritative workbook — the master sheet. Second, a dashboard reads that single master sheet and presents it as clear, navigable views for managers and stakeholders. The defining promise across both stages is trust: the same files always produce the same numbers, and no number reaches the dashboard unless it can be traced back to the exact place it came from.

1.3 Problem statement

Fund reporting data is authoritative but disorderly. The same concept — say, the fair value of a holding, or the net asset value of the fund — appears in different files under different labels, in different positions, in different templates, expressed in different units and currencies, and covering different reporting periods. Today this reconciliation is done by hand. That is slow, expensive, and error-prone, and every re-run risks producing slightly different answers. The core difficulty is not that any single file is hard to read; it is that the collection is heterogeneous and keeps changing shape, while the answer must be exact, repeatable, and defensible.

The product exists to remove that manual reconciliation without lowering the accuracy bar. It must handle files it has never seen, from clients not yet onboarded, in templates not yet designed — and it must never quietly emit a number it cannot justify.

1.4 Goals

Single source of truth
Consolidate a fund's many files into one master sheet that the dashboard and every downstream report read from.
Determinism
The same input always produces the same output, to the number. Re-running an unchanged set of files changes nothing.
Universality
Work on new files and new templates without being re-tuned for each one.
Provable accuracy
Every emitted number is traceable to its source location; anything that cannot be proven is withheld and flagged, never guessed.
Speed and predictability
Process a full fund's file set within predictable time bounds, so users get results on a reliable schedule.
Clarity for non-specialists
Present the consolidated result in a dashboard that a business stakeholder can read without training.

1.5 Non-goals

  • Not an accounting book of record. The system consolidates and presents reported figures; it does not replace the fund's official ledgers or audit.
  • Not a data-invention engine. It never manufactures a value that is absent from the source files. Missing data is disclosed as missing.
  • Not a manual spreadsheet tool. It is not a replacement for hand-editing spreadsheets cell by cell; its value is in automated, repeatable consolidation.
  • Not a trading or execution system. It reports on a fund; it does not transact.

2.1 Personas

Table 1 — Primary personas

2.2 Primary journey: from files to a trusted dashboard

The fund manager or analyst uploads the fund's files as they arrive — often dozens at once, in mixed templates. The system identifies each file, locates the figures inside it, extracts and verifies them, and consolidates everything into the master sheet. Within a predictable time, the dashboard reflects the fund's position. The user did not have to describe the files, map columns, or reconcile anything by hand. The vast majority of figures flow straight through; only genuine ambiguities are surfaced for a decision.

2.3 The review journey: resolving what cannot be proven

When the system cannot prove a figure to its own standard — an unrecognised label, a period that could mean two things, an unfamiliar currency — it does not guess. It holds that item and places it in a short review queue with the exact context needed to resolve it. A user makes the call once; the system records that decision and re-runs, and from then on the same situation is handled automatically for that client. This "hold, resolve once, remember" loop is how the product improves coverage over time without ever compromising on accuracy.

3. The End-to-End System

This section walks the whole product from the outside in: first the layers, then the data flows, then the pipeline stages, the master sheet, and finally the life-cycle of a single file.

3.1 Layered architecture

The product is best understood as five layers stacked between the client's files and the people who read the result. Everything above the master sheet exists to earn the master sheet's trustworthiness; everything below it exists to present that trust usefully. The master sheet is the seam between the two halves of the product and the single point every downstream number passes through.

3.2 Context view (Level 0 data-flow)

At the highest level the system has four counterparties: the source files it reads, the manager who uploads them and resolves the occasional held item, the stakeholder who reads the resulting views, and the oversight function that relies on full traceability. Nothing else crosses the boundary.

3.3 Level 1 data-flow

Opening the box reveals five processes in sequence — identify, extract, validate, consolidate, serve — and two supporting memories: an identity and alias memory that remembers files and the decisions made about them, and a cache that remembers prior results so unchanged work is never repeated. The dashboard (process 5) only ever reads the consolidated master sheet; it never touches raw files.

3.4 The pipeline, stage by stage

The pipeline is a straight line with one branch. A file is identified and checked against the cache; if nothing relevant has changed, prior results are reused rather than recomputed. Otherwise the system locates the structure inside the file, extracts the figures, and verifies them against period, currency and internal totals. Each figure then meets a single gate: if it is provable, it is emitted into the master sheet with a citation to its exact source; if it is not, it is held for review. Held items are resolved once by a person, and the run repeats — so the master sheet only ever contains figures the system could stand behind.

3.5 The consolidated master sheet

The master sheet is the heart of the product: one workbook that consolidates the whole fund. It is organised into a set of purpose-built tabs — a portfolio master, domain tabs for investors and capital, accounting and net asset value, distributions, and compliance, and a bridge tab that the dashboard reads from directly. Every figure it carries is reconciled and carries a reference back to the file and location it came from. Because everything downstream reads only this workbook, there is exactly one version of the truth, and it is fully self-describing.

3.6 The life of a file

The life-cycle makes the fail-closed stance visible: the only way into the master sheet is through validation, and anything that cannot pass waits in "Held" until a person resolves it, after which it re-enters the pipeline. A file is never partially trusted — each of its figures is individually proven or individually withheld.

4. Design Principles & Core Mechanisms

4.1 Design principles

Four principles govern every design decision in the product. They are what make the accuracy promise credible rather than aspirational.

1 · Determinism before everything
The same inputs must always produce the same outputs, to the number. Nothing in the design is allowed to introduce variability into a result.
2 · Fail closed
When the system cannot prove a figure, it withholds and flags it rather than guessing. Silence is safer than a wrong number.
3 · Universality, not tuning
Mechanisms must generalise to files and templates never seen before, rather than being hand-fitted to the examples in front of us.
4 · Provenance for everything
Every emitted figure carries a reference back to the exact place it came from, so any number can be checked at any time.

The third principle deserves a sharp statement, because it is the one most often compromised in systems of this kind. The temptation is always to make something work for the file on the desk today. This product rejects that:

“A mechanism is universal if it works on a file nobody has seen, sent by a client who does not exist yet, in a template that has not been designed yet. That rules out an entire family of tempting solutions.” — Governing design principle for the pre-ingestion layer

In practice this rules out any rule that depends on a specific sheet name, a fixed cell position, a particular column order, or a known client's quirks. Such shortcuts pass today's test and fail the next client's file. The mechanisms described below are chosen precisely because they hold for inputs that do not yet exist.

4.2 Identify vs. extract: the determinism split

The single most important design decision in the product is the division of labour between the AI layer and deterministic code. It is deliberately strict.

  • The AI layer only identifies and locates structure. Its entire job is to answer questions of the form “which row or column holds EBITDA?”, “where is revenue?”, “where are the IRR fields?” — that is, to point at where a figure lives in an unfamiliar layout.
  • Deterministic code performs the actual numeric extraction. Once the location is known, ordinary, repeatable code reads the value, applies units and currency, and records it. The AI layer never produces, computes, adjusts, or invents a number.

This split exists for one reason: to guarantee determinism and repeatability. Because the numbers are always read by deterministic code, the same file always yields the same numbers. Judgement about where to look is separated from the reading itself, so the part of the system that could vary is never the part that produces a value.

4.3 Breaking a document into analysable units

A fund file is not analysed as one undifferentiated blob. Each workbook is broken down into a small hierarchy of self-contained analysable units, and the shape of that breakdown is chosen so that every unit can be understood and verified on its own.

  • The workbook is the outer unit — one file for one purpose.
  • The sheet is the primary working unit. Each sheet is treated as self-contained, so a figure never depends on hidden context from elsewhere in the file.
  • The domain section — a contiguous, labelled block such as a portfolio schedule or a capital account — is the unit the system reasons about when locating figures.
  • The individual figure is the smallest unit: a single value tied to its label, period, currency and exact location. This is the unit that is cited, verified, and either emitted or held.

The rationale for this shape is verifiability. By decomposing to the level of a single cited figure, the system can prove or withhold each value independently, and it can process a large file as a set of small, self-describing pieces rather than one intractable whole. Importantly, values are treated at face value within their unit — the system never stitches a number together from scattered fragments in a way that could hide an error.

4.4 Three-level file identity

Every file is identified at three levels, each answering a different question. Three levels are needed because “is this the same file?” has three genuinely different meanings, and the system must be able to tell them apart.

Byte fingerprint — “is it literally the identical file?”
Distinguishes files by their exact raw contents. If two uploads share a byte fingerprint they are the very same file, and all prior work can be reused without a second look.
Content fingerprint — “are the values the same?”
Distinguishes files by the data they carry, ignoring cosmetic differences such as formatting or re-saving. If the content fingerprint is unchanged, the numbers are unchanged, so verified results still stand even though the file is not byte-for-byte identical.
Layout fingerprint — “is it the same shape?”
Distinguishes files by their structure, setting the actual values aside. If a familiar layout reappears carrying new figures, the system recognises the template and knows how to read it, while still treating the new numbers as new.

Together these let the system make the right economy at each level: reuse everything when a file is identical, reuse verified numbers when only the presentation changed, and reuse structural understanding when a known template returns with fresh data — never confusing one situation for another.

4.5 Period Algebra

Reporting periods are one of the most common sources of silent error in fund data, because the same period is written a dozen ways across files: “Q1”, “quarter ended 30 June”, “three months to Jun-26”, a bare date, a fiscal-year label. The product handles this with Period Algebra.

In Period Algebra a reporting period is a typed object — a first-class thing the system reasons about, not a piece of free text — and normalisation is a total function: every input period resolves to exactly one canonical period, with no undefined cases. There is no input for which the system simply does not know what to do; an expression it cannot resolve confidently is routed to review rather than silently assumed.

Business consequence
Periods never silently mismatch across files, clients, or templates. Two figures are combined only when their periods provably refer to the same span. A figure for one quarter can never be quietly added to, or compared against, a figure for another — the class of error where numbers look consistent but describe different time spans is eliminated by construction.

4.6 Validation, reconciliation & fail-closed handling

Before any figure is emitted it must pass a set of checks: that it was located confidently, that it reconciles with related totals, that its period is unambiguous, and that its currency is known. These checks are combined into a single gate with a strict rule — emit only if everything is provable; otherwise hold. There is no middle setting that lets a doubtful figure through.

This is the mechanism behind the “never a wrong number” promise. The cost of the strict gate is that a small number of items need a human decision; the benefit is that everything on the dashboard is defensible. Every such check is itself tested to confirm it actually blocks the error it targets, so the gate cannot quietly weaken over time.

4.7 Caching

A caching layer sits behind the pipeline so that work is never repeated unnecessarily. When a file — or the structure of a file — has been seen before, the system reuses the results it already proved instead of recomputing them. For the user this buys three things: speed, because unchanged files return almost immediately; cost control, because the expensive understanding step is done once and remembered; and consistency, because reusing a proven result guarantees the same answer as before. The cache is always subordinate to correctness: it is organised around the three-level identity above, so a reused result is only ever served when the identity guarantees it is still valid, and any change that could affect a figure retires the stale result automatically.

5. The Dashboard & Its Outputs

5.1 From master sheet to views

The dashboard is the already-built half of the product. It does not read raw files or re-derive anything; it reads the consolidated master sheet and maps it into views. Because the master sheet is a single, reconciled, self-describing workbook, the dashboard's job is presentation, not reconciliation — which is exactly what keeps the two halves cleanly separated and independently trustworthy.

5.2 The dashboard views

Table 2 — Dashboard views and what they present
ViewWhat it shows
Portfolio & performanceThe fund's holdings, their valuations, and headline performance measures such as multiple on invested capital and rate of return, drawn straight from the reconciled figures.
Investors & commitmentsWho has committed capital, how much has been called and distributed, and each investor's capital position.

ComplianceRegulatory-facing status and the checks relevant to an Indian alternative investment fund, surfaced as clear pass / attention items.

Terms such as “multiple on invested capital”, “rate of return”, “net asset value” and “alternative investment fund” are defined in the glossary (Section 8).

5.3 Outputs, exports & auditability

Beyond the on-screen views, the product produces two durable outputs. The first is the consolidated master workbook itself, which can be downloaded and used as the single reconciled dataset for the fund. The second is an audit trail: for every figure, a reference to the exact file and location it came from, and for every held item, a record of what could not be proven and how it was resolved. Together these mean any number on the dashboard can be traced to its origin, and any decision the system made can be reviewed after the fact.

5.4 Data integrity

Integrity rests on three properties established earlier and simply carried through to the dashboard: determinism (the same files always produce the same views), provenance (every figure is traceable), and fail-closed handling (nothing unverifiable is ever shown). Re-importing an unchanged set of files leaves the dashboard identical; importing corrected files updates exactly the affected figures and nothing else.

6. Assumptions, Dependencies & Security

6.1 Assumptions

  • Source files are genuine fund reporting spreadsheets; the values in them are authoritative even when their layout is inconsistent.
  • Each fund's files are uploaded by an authorised user for that fund; the product organises and consolidates them, but does not judge their business correctness beyond internal reconciliation.
  • Where the source data is genuinely absent, the correct outcome is disclosure of the gap, not estimation.
  • A small, steady volume of held items requiring human resolution is expected and acceptable, and decreases over time as decisions are remembered.

6.2 Dependencies

  • An AI layer used solely to identify and locate structure within files. Its role is bounded by the determinism split in Section 4.2; it never produces numbers.
  • The consolidated master sheet as the contract between the two halves of the product. The dashboard depends on its structure, not on any raw file.
  • Per-client memory of resolved decisions and file identities, which is what lets coverage improve without re-tuning.

Specific technologies, vendors, and internal components are intentionally out of scope for this document.

6.3 Security & access posture

At the policy level, the product is designed around strict separation of each client's data. Fund data is scoped to its owning organisation, so one client's files, master sheet, and dashboard are never visible to another. Access to the dashboard and to uploads is authenticated, and actions that change data are attributable to a user. Because every figure is traceable to its source and every held decision is recorded, the system is auditable by design. Data is retained as the reconciled master sheet plus its audit trail; source files are retained as needed to support that trace.

7. Risks, Metrics & Roadmap

7.1 Risks & mitigations

Table 3 — Key risks and how the design mitigates them
RiskMitigation built into the design
A wrong number reaches the dashboard.Fail-closed gate: figures are emitted only when provable; everything else is held. Each check is tested to confirm it actually blocks its target error.
Two runs of the same files disagree.Determinism split: all numbers are read by deterministic code, and identical inputs are proven to produce byte-identical output.
A new client or template breaks the system.Universality principle: no mechanism depends on a known sheet, column, or client. Unfamiliar structure is located generically or held, never mis-read.
Periods or currencies are silently mismatched.Period Algebra resolves every period to one canonical form or holds it; unknown currencies are disclosed rather than assumed.
Growth in file volume slows delivery.The pipeline is engineered to process a full fund's file set within predictable time bounds, and caching removes repeated work.
Held items overwhelm users.“Resolve once, remember”: each decision is recorded per client, so the review queue shrinks over time.

8. Glossary

AI layer / identification model
The part of the system that locates structure — which row or column holds a given figure. It never produces or alters numbers.
Alternative Investment Fund (AIF)
A privately pooled investment vehicle regulated in India; the fund type this product serves.
Analysable unit
A self-contained piece of a document the system reasons about — a sheet, a labelled section within it, or a single figure.
Byte fingerprint
An identity check answering “is this the exact same file?” based on its raw contents.
Content fingerprint
An identity check answering “are the values the same?”, ignoring cosmetic differences.
Layout fingerprint
An identity check answering “is this the same shape/template?”, ignoring the actual values.
Caching layer
A memory of prior results that lets unchanged work be reused, for speed, cost control, and consistency.
Consolidated master sheet
The single reconciled workbook that all downstream views and reports read from; the fund's one source of truth.
Determinism
The property that the same inputs always produce the same outputs, exactly.
Distribution
Cash returned by the fund to its investors.
Fail closed
The stance of withholding and flagging anything that cannot be proven, rather than guessing.
General Partner (GP)
The fund manager. Limited Partners (LPs) are the investors.
Hold
The state of a figure that could not be proven and is routed to review instead of being emitted.
Multiple on Invested Capital (MOIC)
How many times the invested capital is currently worth; a headline performance measure.
Net Asset Value (NAV)
The fund's total value less its liabilities.
Period Algebra
Treating a reporting period as a typed object and normalising every period expression to exactly one canonical period, or holding it — so periods never silently mismatch.
Provenance / citation
The reference stored with every emitted figure pointing to the exact file and location it came from.
Rate of return (IRR)
A time-sensitive measure of the fund's return to investors.
Review queue
The short list of held items awaiting a human decision; decisions are remembered per client.
Total function (in Period Algebra)
A mapping defined for every possible input — there is no period expression the system leaves undefined.
